# Fase 1.2 — KYC y Google OAuth

## Objetivo

Completar los dos features de autenticación e identidad que quedaron fuera del alcance de Fase 1: el wizard de verificación de identidad (KYC) por rol y el login/registro con Google (OAuth). Ambos son independientes entre sí y pueden construirse en cualquier orden.

---

## Feature A — Google OAuth

### Prerequisitos
- Proyecto de Google Cloud con OAuth 2.0 configurado para la app (Android + iOS)
- Client IDs registrados en Supabase → Authentication → Providers → Google
- Para iOS: si se habilita Google Sign-In en App Store, Apple exige ofrecer también "Sign in with Apple" (Guideline 4.8) — coordinar antes de publicar

### Alcance
- Reemplazar los placeholders/alertas de "Continuar con Google" en login y registro por el flujo real de OAuth
- Usar `expo-auth-session` o `@react-native-google-signin/google-signin` (confirmar con Ricardo cuál ya está instalado o se prefiere)
- Al autenticar con Google por primera vez: si el usuario no tiene `rol` asignado → redirigir a `role-select` igual que el flujo de registro con correo
- Si ya tiene rol → directo a tabs
- Manejar el caso de email ya registrado con contraseña (Supabase devuelve error específico — mostrar alerta "Usa tu contraseña para entrar")

### Criterios de aceptación
- Login con Google funciona en Android
- Login con Google funciona en iOS
- Primera vez → pasa por role-select
- Regreso → directo a tabs
- Error de email duplicado muestra mensaje claro

## Feature B — KYC / Wizard de documentos de identidad

### Prerequisitos de esquema
⚠️ Confirmar con Ricardo antes de construir:
- Tabla de documentos de identidad ligada a `usuario_id` (no a un rol) — existe o crear
- Columnas necesarias: `tipo_documento` (INE, pasaporte, etc.), `url_anverso`, `url_reverso`, `url_selfie`, `estatus_kyc` (pendiente, aprobado, rechazado), `motivo_rechazo`
- Bucket privado en Supabase Storage para archivos KYC (URLs firmadas, nunca públicas)
- Políticas RLS: el usuario solo puede ver sus propios documentos; el admin puede ver todos

### Documentos requeridos por rol (confirmar detalle exacto con Dalia antes de construir)

| Documento | Comprador | Vendedor | Asesor |
|---|---|---|---|
| INE (frente + reverso) | ✅ | ✅ | ✅ |
| Selfie de verificación | ✅ | ✅ | ✅ |
| Constancia de situación fiscal | Opcional | ✅ | ✅ |
| Acta de nacimiento | — | ✅ | ✅ |
| Foto de perfil profesional | — | — | ✅ |

> "Usar INE" o "Usar pasaporte mexicano" como alternativa en el paso de identificación — pasaporte pide solo anverso + selfie.

### Flujo del wizard (4 pasos)

1. **Identificación** — seleccionar INE o Pasaporte → capturar fotos (cámara o galería)
2. **Selfie** — foto de verificación de rostro
3. **Documentos adicionales** — según rol (paso visible solo si el rol requiere documentos extra)
4. **Resumen** — muestra todo lo subido, botón "Enviar para revisión"

El wizard debe:
- No dejar avanzar sin subir los documentos obligatorios del paso actual
- Permitir saltar pasos de documentos opcionales
- Guardar progreso (si el usuario cierra a mitad, retomar desde donde estaba)
- Subir archivos a Supabase Storage al avanzar (no al final del wizard)

### Dónde se accede
- Desde la pantalla de Perfil → opción "Verificación de identidad" (actualmente `onPress: () => {}` vacío)
- Badge "Verificación pendiente" del perfil debe llevar a este wizard al tocarse

### Criterios de aceptación
- El wizard muestra los pasos correctos según el rol del usuario
- Documentos obligatorios bloquean el avance si no se suben
- Archivos van a bucket privado (verificar URL firmada, no URL pública)
- Al terminar, `estatus_kyc` pasa a `pendiente` en Supabase
- Retomar el wizard a mitad del proceso muestra el progreso anterior
- El badge del perfil actualiza su estado cuando el admin aprueba/rechaza (requiere polling o realtime)
